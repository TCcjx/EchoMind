# EchoMind Python 改动说明

本文记录这次围绕“多 Agent 编排、工具调用可追踪、请求级可回放、接口可查询”做的改动。

## Python 版改动

### 1. 多 Agent 编排链路重构
- 这次 Python 版不只是“多个 Agent 各写一个不同 prompt”，而是把多 Agent 编排做成了完整链路。
- 在 `agents/agent_orchestrator.py` 中，Agent 响应和编排结果都扩展为可携带工具信息。
- `AgentResponse` 增加了 `tools_used` 和 `tool_traces`。
- `OrchestratorResult` 也增加了 `tools_used` 和 `tool_traces`，便于把一次请求里实际发生过的工具调用完整带出去。
- `Request` 里带了 `request_id`，让多 Agent 协作、工具调用和最终响应能串成同一条链。

### 2. 多 Agent 路由从“分角色回答”升级为“结构化编排”
- `AgentProfile` 不再只是提示词壳子，而是把 Agent 的角色、职责、工作流、输入输出契约、升级条件、工具范围都结构化了。
- 这意味着 Agent 的差异不只是“system prompt 不同”，而是“角色契约 + 工具边界 + 协作方式”都不同。
- `RoutingDecision` 显式描述：
  - `primary_agent`
  - `supporting_agents`
  - `reason`
  - `confidence`
- 路由逻辑分成三层：
  - 意图路由
  - 性能路由
  - 降级路由
- 对复杂问题会走并行协作，不是只挑一个 Agent 硬答。

### 3. 并行协作和升级机制补齐
- `run_parallel` 会把一个请求同时派给多个 Agent。
- 最终结果会合并多个 Agent 的回答，而不是只保留某一个 Agent 的输出。
- 升级机制也保留在编排层：
  - `CRITICAL` 紧急度直接升级
  - `ESCALATION` / `HUMAN_HANDOFF` 直接转人工
  - Agent 自己也可以在回答里触发升级信号

### 4. Tool Scope 和共享工具接入
- `BaseAgent` 里引入了工具白名单和共享工具注入。
- `agents/tools.py` 统一定义了可用工具，Agent 只拿到自己 scope 里的工具。
- 这让多 Agent 不再只是“不同角色说不同话”，而是“不同角色可调用不同工具”。

### 5. Tool Use 过程可记录
- `BaseAgent` 里保留并输出每次 tool call 的明细。
- 记录字段包括：
  - `tool_name`
  - `success`
  - `fallback_used`
  - `cached`
  - `reranked`
  - `latency_ms`
  - `error`
- 这样可以从一次对话直接追到具体调用了哪些工具、是否成功、耗时多少。

> 更正：这一条当时并没有真正生效，成功返回的 `tool_traces` 一直是空列表；当时列出的 `fallback_used` 字段也根本不存在，
> 实际字段是 `agent_type`、`tool_name`、`tool_use_id`、`input`、`success`、`result_success`、`latency_ms`、`cached`、`reranked`、`error`。
> 空列表和 `fallback_used` 都在 2026.09.27 修好，见文末。

### 6. 请求级 trace 存储
- `AgentOrchestrator` 增加了最近请求 trace 缓存。
- 新增能力：
  - `get_tool_trace(request_id)`
  - `get_recent_tool_traces(limit)`
- 每次 `/chat` 结束后都会记录一条 request trace，便于排查和回放。

### 7. API 暴露
- 在 `api/main.py` 中补了工具轨迹查询接口：
  - `GET /trace/tool/{request_id}`
  - `GET /trace/tools?limit=20`
- `/chat` 响应里也带上了 `request_id`，方便前后串联。

### 8. 这次 Python 侧的目标
- 让一次请求从“用户输入”到“意图识别”再到“工具调用”都能被查到。
- 不是只看最终回答，而是能看见中间发生了什么。

## 2026.09.27 修复

这一节记录上面第 5、8 两条目标当时未真正落地的部分，以及另外两个缺陷。三处修复都补了可在无外部依赖环境下运行的回归测试（`tests/`，用假 LLM 客户端和假 ChromaDB collection）。

### 1. 成功请求的 `tool_traces` 恒为空
- 原因：`_call_llm` 只在返回前赋值 `self._last_tools_used`，`self._last_tool_traces` 仅在轮数耗尽的抛出路径才赋值，
  所以正常走完工具循环的成功响应里 `tool_traces` 永远是 `[]`，`/trace/tool/{request_id}` 拿不到明细。
- 改法：`_call_llm` 改为返回 `(content, tools_used, tool_traces)` 三元组，删除实例上的 `_last_tools_used` /
  `_last_tool_traces` 字段（这两种轨迹状态挂在共享的单例 Agent 上不利于并发请求）；
  轮数耗尽时抛出 `ToolRoundExhausted`，由 `handle()` 单独捕获，把已经发生的轨迹带进失败响应。

### 2. 意图识别的 Few-shot 示例从未进入 prompt
- 原因：`_llm_recognize` 先把 `_TEMPLATES` 拼成 `examples` 字符串，但 prompt 模板里没有插入它，
  权重最高（0.7）的那一路实际是 zero-shot。
- 改法：prompt 增加 `参考示例:` 段落并插入 `{examples}`，每类意图取 1 条样本以控制长度。

### 3. 重复导入同一篇知识文档会整批失败
- 原因：`doc_id` 由「标题 + 切片序号 + 片段前缀」确定性生成，重复导入必然命中已有 ID，
  而 `add_documents` 用的是 `collection.add()`，ChromaDB 会抛重复 ID 错误，整批导入一起失败；
  同时启动时的 `_load_default_docs` 也走这条路径。
- 改法：改用 `collection.upsert()`，并在单批内先按 `doc_id` 去重。

### 4. 工具降级被当成调用成功
- 原因：`MCPToolManager._fallback_result` 在真实 handler 抛错或熔断打开时返回 `success=True`，
  而 `ToolResult` 里没有任何降级标记。下游只看 `success`，于是「知识库全挂 + 返回一句降级话术」
  和「真实命中知识库」完全一样：`search_with_rewrite` 会把降级文案混进 Top-K 喂给模型，
  `/search`、Agent 工具轨迹和前端也都显示成功。
- 改法：`ToolResult` 增加 `fallback_used` 字段（统计口径不变，底层调用仍记 `failed`），
  `search_with_rewrite` 只把降级文案作为「全部子查询都失败」时的兜底，部分失败时结果里不含降级条目但整体标记降级；
  该标记沿 `search_knowledge_base` 工具返回值 → Agent 工具轨迹 → `/search` 响应向上传递，
  工具返回值里额外带 `warning` 提示模型不要引用降级内容作为事实依据。

### 5. 召回去重键被 score 破坏
- 原因：`search_with_rewrite` 用 `md5(str(item))` 作为去重键，而 `knowledge_base.search` 返回的每条结果都带
  本次子查询的 `score`；同一片段被不同子查询命中时 score 必然不同，去重永远不会命中，
  合并结果里塞满重复片段，挤占重排输入和 Top-K 名额。
- 改法：去重键改为剔除易变字段（`score`/`distance`/`similarity`/`rerank_score`）后的稳定身份，
  重复命中时保留最高分；写入前复制一份，避免把分数写回缓存中的原始结果对象。

### 6. Windows/GBK 终端下服务启动即崩
- 现象：在中文 Windows 上直接 `uvicorn api.main:app`，lifespan 里 `print(BANNER)` 抛
  `UnicodeEncodeError: 'gbk' codec can't encode character '\u0295'`，进程在打印小熊图案时就退出，
  后面的组件初始化根本不会执行。
- 原因：控制台默认编码是 GBK，而 BANNER 里的 `ʕ•ᴥ•ʔ` 和 `╔══╗` 框线字符不在 GBK 字符集内，
  Python 的 stdout 默认 `errors="strict"`。
- 改法：`api/main.py` import 时把 stdout/stderr 改为 `errors="replace"` 兜住崩溃；
  再提供 `_banner()`，检测 `sys.stdout.encoding`，编码不下时退回 ASCII 版图案，
  避免演示截图里出现一排 `?`。UTF-8 终端（Docker/Linux/macOS）仍是原来的小熊图案。

### 7. Redis 不可用时 /chat 直接 500
- 现象：没有 Redis 时（例如只起 API 不起 `docker compose`），第一轮对话就会 500，
  栈停在 `conversation_memory` 的 `lrange` / `get` / `lpush` 上。
- 原因：三级记忆里只有 ChromaDB 那两路做了容错，读写 Redis 的三处是裸调用，
  异常直接冒泡到 `/chat`。
- 改法：`_get_working_memory` 读失败按「没有历史」返回 `[]`，并跳过解析失败的单条脏数据；
  `get_context` 的会话摘要读失败按空摘要继续；`add_message` 的写入（含触发的压缩）整段容错，
  只记 warning。口径是「Redis 是加速器不是数据源」——挂掉时丢的是这一轮上下文，而不是用户的答案。

## Java 版改动（历史存档）

> 本节记录的是当天 Java 版的改动。Java 版实现已于 2026-09-27 从本项目中移除，当前只维护 Python 版；
> 下文保留原文，仅作历史记录用。

### 1. 请求 ID 打通
- `AgentRequest` 支持显式传入 `requestId`。
- `ChatResponse` 增加 `request_id`。
- `/chat` 返回结果现在可以直接拿 `request_id` 去查 trace。

### 2. Agent / Orchestrator 返回结构扩展
- `AgentResponse` 增加了工具相关字段：
  - `toolName`
  - `toolSuccess`
  - `toolCached`
  - `toolReranked`
  - `toolError`
- `OrchestratorResult` 增加了：
  - `toolsUsed`
  - `toolCalls`

### 3. 多 Agent 编排保持不变但补了轨迹
- Java 侧仍然是多 Agent 编排结构：
  - `GENERAL`
  - `TECHNICAL`
  - `BILLING`
  - `ESCALATION`
- `AgentOrchestrator` 依旧负责路由、并行协作和降级。
- 这次主要补的是：
  - 多 Agent 结果上报工具轨迹
  - 请求级 trace 落库/落存储
  - 方便对单次请求做回放和排查
- 当前 Java 版还没有完全变成 Python 那种“Agent 内部 LLM tool-use 循环”，但多 Agent 的请求聚合和可观测性已经补上了。

### 4. 新增 trace 包
- 新增 `com.echomind.trace`：
  - `ToolCallTrace`
  - `RequestToolTrace`
  - `RequestTraceStore`
- 这部分负责把一次请求的工具调用、耗时、是否命中缓存、是否重排等信息统一存下来。

### 5. Controller 暴露查询接口
- `EchoMindController` 新增：
  - `GET /trace/tool/{requestId}`
  - `GET /trace/tools?limit=20`
- 同时 `/chat` 会把知识库检索结果也作为外部工具 trace 带进编排结果。

### 6. 当前 Java 侧的特点
- 这次 Java 版先做的是“请求级工具轨迹可查”。
- 和 Python 版相比，Java 目前还不是完整的 LLM tool-use 循环闭环，但已经能把一次请求里发生的工具行为查询出来。
